## Models and agents

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Microsoft Foundry | The Azure platform used to manage models, agents and evaluations. | The notebooks connect to a Foundry project. |
| Foundry project | A place to organize agents, connections and evaluation resources. | Its endpoint selects the project a client uses. |
| Model | A trained system that generates a response from input. | A chat model writes answers; an embedding model represents text as numbers. |
| Model deployment | A named configuration that makes a model available to call. | Code uses the deployment name, which can differ from the model's catalog name. |
| Model version | A particular release of a model. | Changing it can affect answers even if the deployment name stays the same. |
| Project endpoint | The HTTPS address used to reach a Foundry project. | An address, not a password; the caller still needs authorization. |
| Prompt | The input sent to a model for a request. | A question plus any supplied context. It does not retrain the model. |
| Instructions | Rules describing the assistant's role and expected behavior. | They guide answers but do not replace permissions or code-enforced checks. |
| Responses API | The API used to request model or agent responses, including tool calls. | Called through `client.responses.create(...)`. |
| Model token | A unit of text processed or generated by a model. | Token counts measure usage. A token is not always a whole word. |
| Agent | A configured model with instructions and, optionally, tools. | The prompt agents in these labs have saved definitions in Foundry. |
| Agent version | A saved, fixed agent definition. | Changing instructions creates another version; it does not rewrite an existing one. |
| Agent reference | The name and version identifying the agent to invoke. | Selects a saved definition, not unsaved notebook edits. |
| Conversation | Stored messages that give later requests earlier context. | Enables follow-up questions without treating each one as unrelated. |

## Azure resources and access

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Resource group | A named collection of Azure resources managed together. | Can contain the Foundry account, Search service and storage account. |
| Foundry account | The Azure resource that contains Foundry projects and model deployments. | Account-level RAI policies are managed here too. |
| Microsoft Entra ID | The identity service used to sign in and obtain access tokens. | `az login` signs in the notebook operator. |
| Authentication / authorization | Authentication establishes who is calling; authorization decides what that identity may do. | Being signed in does not automatically grant Search or Foundry access. |
| RBAC | Role-based access control: permissions granted through roles at a chosen scope. | `Search Index Data Reader` allows an identity to read Search index data. |
| Managed identity | An Azure-managed identity for a resource or service. | The Foundry project's identity can access the knowledge base independently of your account. |
| Project connection | Configuration telling a project how to reach and authenticate to another service. | The knowledge-base connection uses the project's managed identity. Other connection types can use different authentication. |
| Access token | A short-lived credential presented to a service. | Not a model token. Do not save it in source code or notebook outputs. |
| Region | An Azure location where resources can be provisioned. | Model availability does not guarantee Search availability in the same region. |

## Retrieval and sources

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Retrieval | Finding relevant information in a source collection. | Search selects passages from the WHO guidelines. |
| RAG | Retrieval-augmented generation: retrieve evidence, then give it to a model when generating an answer. | Avoids putting every source document in the prompt. |
| Grounding | Basing an answer on supplied evidence rather than unsupported model memory. | The assistant should acknowledge when the retrieved guidelines do not answer the question. |
| Chunk | A passage split from a larger document for retrieval. | A PDF produces many searchable chunks. |
| Search index | A searchable collection of records and their fields. | Holds guideline chunks, vectors and citation metadata. Uploading a PDF alone does not create these records. |
| Metadata | Descriptive fields attached to content. | `document_title`, `publication_id`, `source_url` and `license` describe each passage. |
| Embedding | A numeric representation used to compare meaning. | Helps match related wording such as "high blood pressure" and "hypertension". |
| Vector search | Retrieval based on similarity between embeddings. | Can find related passages without an exact keyword match. |
| Hybrid search | Keyword and vector searches combined into one result set. | Not the same thing as semantic ranking. |
| Semantic ranking | A second pass that reranks retrieved results for relevance to the query. | Labs inspect the order of semantically ranked results. |
| Knowledge source | A source described so that a knowledge base can retrieve from it. | The WHO Search index is one knowledge source. |
| Knowledge base | A managed retrieval service over one or more knowledge sources. | Can be queried directly or connected to an agent as a tool. |
| Foundry IQ | Managed knowledge retrieval used to ground agents in connected sources. | The workshop accesses it through an Azure AI Search knowledge base. |
| Agentic retrieval | Model-assisted planning and execution of searches for a question. | May split a question into several subqueries. |
| Generation context | The exact evidence supplied to the answer model. | An expected publication may be found without every needed fact reaching this context. |
| `extractiveData` | A knowledge-base output mode that returns evidence instead of writing the final answer. | Lab 13 uses a separate model to answer from that evidence. |
| Reference / citation | A reference identifies a source; a citation links a claim to supporting material. | `[S1]` labels Search context; `ref_id` identifies an IQ reference within a response. Valid IDs do not prove claims are supported. |
| Publication filter | A retrieval condition limiting results to a publication. | The IQ benchmark uses `publication_id` to control the source. It does not test unfiltered source selection. |

## Tools and workflows

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Tool | A capability an agent can request, described by its name, purpose and inputs. | Tool availability and instructions are separate: describing a tool in a prompt does not attach it. |
| Function tool | A tool whose function is executed by the calling application. | Foundry requests a call; the notebook runs the Python function and returns its result. |
| MCP | Model Context Protocol: a way for an agent to discover and call tools on another server. | The knowledge base exposes a remote MCP tool. |
| Tool call / result | A request to perform an operation, and the data returned from that operation. | A request to schedule a review is not proof that a booking occurred. |
| Call ID | An identifier connecting a tool result to the call that requested it. | `call_id` is used in the Responses API round trip; saved evaluation messages use matching tool-call identifiers. |
| Round trip | Receiving a tool call, executing it, returning the result and asking the model to continue. | Return a result for each function call, including when several calls arrive together. |
| JSON Schema / strict schema | Rules for a JSON object's fields and values; strict tool schemas constrain generated arguments to that shape. | `required` lists mandatory fields; `additionalProperties: false` rejects extra fields. Correct shape does not prove correct values or authorization. |
| Orchestration | Code coordinating which agents run and how their results are passed along. | Microsoft Agent Framework runs the lab's researcher and summarizer in sequence. |
| Participant / sequential workflow | A participant is one agent in the workflow; a sequential workflow runs participants in order. | The summarizer receives the researcher's findings. A handoff is not independent fact-checking. |
| `output_from` | The workflow setting selecting which participant results are returned for inspection. | `"all"` exposes both steps without changing their execution order. |

## Safety and red teaming

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Guardrail | A runtime safety policy applied to a deployment or agent. | It can detect or block configured risks, but does not prove factual correctness. |
| RAI policy | The Azure resource storing a Responsible AI guardrail configuration. | Lab 5 creates a custom policy at account scope. |
| Control | One configured check within a guardrail. | Defines what to inspect and whether to block it. Inspect actual settings rather than assuming defaults. |
| Indirect attack | An instruction hidden in content the assistant reads, rather than in the user's direct request. | A retrieved document might try to redirect the assistant. |
| Safety annotation | Response metadata describing a safety detection or filtering decision. | Different from a source citation. |
| Application policy | Rules enforced by your own application code. | An exact hospital identifier rule or an approval requirement. |
| Approval gate | A decision enforced before an operation is executed. | Local function writes need a local gate; MCP approval settings do not protect them automatically. |
| Abstention / insufficient evidence | Declining to answer a part that the supplied sources cannot support. | A safe abstention can still fail a completeness gate; it should not be replaced with invented facts. |
| Red teaming | Deliberately testing whether an assistant can be induced to cross a defined boundary. | Use synthetic, isolated scenarios without consequential tools. |
| Risk register | A record of risks, owners, required controls and evidence plans. | States which behavior is prohibited and who must review it. |
| Risk taxonomy | Reviewed categories that guide generated safety tests. | Enabled categories define the cloud test scope; a generated draft is not approval. |
| Attack strategy | A transformation that presents a test prompt differently. | The lab uses `Flip` and `Base64` within the reviewed scope. |
| Attack Success Rate (ASR) | The fraction of evaluated attack attempts judged to cross the tested boundary. | Lower is better only for that test scope. Missing metrics or contradictory results can make the rate unusable. |

## Tracing and observability

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Observability | Collecting evidence about what a system did and how it behaved. | Tracing helps explain a request; evaluation judges its quality. |
| Trace | A set of related operations recorded for a request. | A view can be incomplete if spans were not recorded, exported or linked. |
| Span | One timed operation within a trace. | An agent call or an evidence check. |
| Parent / child spans | Relationships showing which operation started another. | An application span can contain the agent-request span. |
| Trace ID / propagation | The ID groups spans; propagation passes the needed trace context between components. | Links client and service work into the same trace. |
| Attribute | A label or value recorded on a span. | Scenario and data-classification labels help investigate requests. |
| Instrumentation / tracer | Instrumentation records operations; a tracer creates custom spans. | SDK instrumentation and notebook-defined spans complement each other. |
| OpenTelemetry | Standard APIs and tools for collecting and exporting telemetry. | Used to instrument the notebook's calls. |
| Application Insights | Azure's application monitoring service. | Receives telemetry; the Foundry project needs the appropriate connection. |
| Content recording | Storing prompts, answers or tool content in telemetry. | Disabling client-side recording does not automatically disable service-side recording. |
| Activity records | Operation details returned by IQ retrieval. | Include planning, Search calls, timing and warnings; they are not the same as OpenTelemetry spans. |

## Evaluation design

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Evaluation / evaluation run | An evaluation defines inputs and checks; a run applies that definition to data. | Baseline and repaired runs can share one evaluation definition. |
| Evaluator / judge | A check that assesses one aspect of a result. | Some checks are exact Python rules; model-based judges return scores or labels and reasons. |
| Deterministic check | An exact rule that gives the same result for the same input. | The local approval and tool-argument checks do not need a model judge. |
| Semantic evaluation | Judging meaning rather than only matching exact values. | A model can assess whether an answer makes sense, but its scores may vary. |
| Benchmark | A fixed set of cases and expectations used for comparison. | Labs 12 and 13 share WHO topics and versioned expectations. |
| Ground truth / reference answer | An expected answer written for evaluation. | Kept separate from generation inputs; its accuracy still needs review. |
| Data mapping | The connection between a dataset field and an evaluator input. | Tells the judge which text is the question, answer or context. |
| Answer contract | The required answer parts and citation rules declared before generation. | The generator must answer each part from evidence or mark it unsupported. |
| Baseline | The original behavior or scores retained for comparison. | Keep failing examples when evaluating a repaired copy. |
| Regression case / known-bad case | A case kept to catch behavior changes; a known-bad case is deliberately incorrect. | The wrong-ward example must fail before its repair. |
| Oracle | The expected result used by an exact test. | The expected tool name and complete arguments in Lab 10. |
| Normalization | Removing irrelevant representation differences before comparison. | Ignore transport IDs, not tool arguments or call order. |
| Trajectory | The ordered request, tool calls, results and final answer. | An acceptable final sentence can hide an unauthorized earlier action. |
| No-tool case | A case where the correct behavior is to make no tool call. | Protects against unnecessary reads or writes. |

## Quality measures

The retrieval definitions below describe this workshop's publication-based
benchmark, not a universal definition of relevant evidence.

| Term | Meaning | What it does not prove |
| --- | --- | --- |
| Recall@k | The fraction of expected evidence groups represented in the first `k` results. | Finding the publication does not prove the right passage was selected. |
| Precision@k | The fraction of the inspected top results belonging to expected publications. | Those passages may still omit needed facts. |
| Reciprocal rank | One divided by the rank of the first expected result; zero if none is found. | Early placement is not proof of a complete answer. |
| Context-signal coverage | The fraction of predefined word-or-phrase groups found in the context. | Keyword matches do not establish sufficient evidence. |
| Answer-part coverage | The fraction of required parts represented by answer claims. | A claim's presence does not establish correctness or support. |
| Citation coverage | The fraction of claims carrying source citations. | The cited source may be invalid or may not support the claim. |
| Citation validity | The fraction of cited IDs belonging to sources supplied for that answer. | A valid ID does not mean the claim faithfully represents the source. |
| Groundedness | How well an answer is supported by its supplied context. | The source itself may be incomplete or incorrect. |
| Relevance | How well the response addresses the request. | A generic judge may score a safe abstention poorly. |
| Response Completeness | How much of the expected answer the response covers. | A complete-sounding answer can still lack support. |
| Task Adherence | Whether an agent followed its instructions and constraints. | A model-based score cannot override an exact authorization rule. |
| Task Completion | Whether the outcome was appropriate for the permitted task. | Completing an action without required approval is not acceptable. |
| Tool Output Utilization | Whether the answer accurately uses the tool results. | The agent might still have selected the wrong tool. |
| Tool Selection | Whether the chosen tool was appropriate and necessary. | It may receive the wrong arguments. |
| Tool Call Accuracy | Whether the tool choice and its inputs make sense for the request. | Model judgement does not replace exact checks of required values. |

## Repeats, performance and cost

| Term | Meaning | In this workshop |
| --- | --- | --- |
| Frozen answer | A saved response kept unchanged during scoring. | Avoids generating new answers until one passes. |
| Live repeats / judge repeats | Live repeats rerun retrieval and generation; judge repeats rescore the same saved answer. | Separate system variability from evaluator variability. |
| Median | The middle value when scores are sorted; with an even count, the mean of the two middle values. | Labs use an odd number of repeated judge scores. |
| Release gate | Predetermined conditions for accepting a result. | `ship` means the workshop checks passed, not clinical approval. `mitigate` means a required check failed. |
| Worst-case summary | A report retaining the weakest quality across repeated runs. | One passing repeat cannot cancel a failed one. |
| Partial IQ result (HTTP 206) | An IQ retrieval response indicating that only part of the requested retrieval completed. | Inspect source warnings; returned evidence alone does not make the run fully successful. |
| Latency / p95 latency | Latency is elapsed time; p95 is the time at or below which 95% of observed durations fall. | The helper uses nearest rank. With three samples, p95 is the slowest sample, not a reliable production estimate. |
| Usage / cost estimate | Usage counts consumed tokens and requests; an estimate applies supplied prices to them. | Missing prices mean unknown cost, not free usage. An estimate is not an Azure bill. |
| Quota / rate limit | Quota bounds allocated capacity; rate limits restrict requests or tokens over time. | Available quota and regional service capacity are separate constraints. |
